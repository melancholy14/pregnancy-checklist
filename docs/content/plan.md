## 2. Phase 5 — 도구 고도화 + 콘텐츠 자산 확장

> 출처: [`docs/plan/plan.md`](../plan/plan.md) §Phase 5 + Phase 4·4.5 이월 항목 (`docs/content/backlog.md` A·B 그룹)

### 2.1 Scope (현재 가설)

**In scope (기획 관점):**

- 체중 차트 BMI별 권장 범위 시각화 (구 Phase 4 Step 1)
- 영상 채널 디렉토리 페이지 (`/info/channels` 또는 `/channels`)
- 통합 태그 2단계 계층 필터 — **콘텐츠 ≥20건 도달 시**
- 큐레이션 컬렉션 카드 — **운영 리듬 안정 시**
- 블로그 front matter 태그 정규화 일괄 마이그레이션
- 베이비페어 크롤러 (`scripts/crawl-babyfair.ts`) — 원래 Phase 5 핵심
- 베이비페어 Admin 검수 (CLI 기반)

**Out of scope (Phase 6+로 이월):**

- 회원가입 / 로그인
- 남편과 체크리스트 공유 (체크 상태 자체 공유 — URL 인코딩 또는 서버 필요)
- 여러 기기 동기화
- PWA / 푸시 알림 (notification_opt_in 데이터 누적 후 재평가)
- API Routes 기반 베이비페어 Admin (Phase 6 GCP 전환 후)

### 2.2 우선순위 결정의 핵심 변수

Phase 5 착수 시점에 운영자가 다음 데이터로 우선순위를 재정렬한다:

| 데이터 출처 | 결정에 어떻게 쓰나 |
|-----------|-------------------|
| `search_submit` (results_count=0) TOP | **콘텐츠 백로그** — 어떤 글을 먼저 쓸지 |
| `external_link_click` TOP 도메인 | **자체화 후보** — 어떤 가이드를 자체 페이지로 만들지 |
| `article_read_complete` ↔ 체크리스트 진입률 | 어떤 글이 도구 흐름을 만드나 |
| 코호트 W+1·W+4 리텐션 | 후기 주차 콘텐츠가 부족한가, 초기 주차가 부족한가 |
| `notification_opt_in` 가설 데이터 | PWA·푸시 우선순위 |

### 2.3 BMI 차트 강화 — 선행 작업 체크리스트

법적 리스크가 높은 항목이므로, 코드 작업 전에 다음이 마무리되어야 한다.

- [ ] 의료 면책 프레임워크 강화 (현재 일반 디스클레이머만)
- [ ] 개인정보처리방침에 **건강 정보 수집·저장 조항** 추가 (BMI 산출용 키·체중)
- [ ] IOM 2009 권장 범위 데이터 정리 (1차 소스 명시)
- [ ] 의료기기법 저촉 여부 법무 자가 점검 (그래프 = 의료 영상이 아닌지)
- [ ] 차트 하단 면책 직접 배치 (별도 페이지 X — UX와 면책의 거리 최소화)

### 2.4 채널 디렉토리 — UX 결정 사항

- 라우트: `/info/channels` vs `/channels` (`/info` 통합과의 IA 정합성)
- 채널 카드: 검증 기준·분류(예: 의료 전문가 / 임산부 / 육아 / 산후) 정의
- 채널 상세 페이지: 채널 메타 + 큐레이션 영상 리스트
- 영상 카드 채널명 → 채널 상세 deep link

### 2.5 베이비페어 크롤러 — 기획 관점

- **원래 Phase 5의 핵심 항목.** 데이터 신선도가 베이비페어 페이지 가치의 본질
- 현재 운영자 수동 입력 — 한계 있음 (전국 행사 누락 가능)
- 크롤 → 정규화 → CLI 검수 → 빌드 재배포 흐름
- **승인 기준이 콘텐츠 정책**: 광고성 행사 제외 / 입장료 0원 명시 / 행사 종료 후 N일 자동 비활성

### 2.6 작업 순서 권장

1. **Phase 4.5 G·H 이벤트 1~2주 누적** (데이터 없이 우선순위 못 정함)
2. **베이비페어 크롤러** 먼저 — 운영 부담 감소가 직접적
3. **콘텐츠 매트릭스 갱신** + 글 추가 (운영자 경험 도래에 따라)
4. **채널 디렉토리** — `/info` 사용 패턴 데이터 본 뒤
5. **BMI 차트** — 법적 선행조건 마감 후
6. **태그 2단계 필터** — 콘텐츠 ≥20건 도달 후

## 3. Phase 6 — GCP 인프라 전환

> 출처: [`docs/plan/plan.md`](../plan/plan.md) §Phase 6

### 3.1 기획 관점에서의 의미

`output: 'export'` 정적 빌드 → standalone Next.js + GCS 데이터 소스 + API Routes로 전환.

**왜 전환하는가 (기획 관점):**

- 베이비페어 같은 **운영 데이터 갱신 빈도가 높은 도메인**은 정적 빌드+재배포 사이클이 부담
- 회원가입·푸시 같은 미래 기능은 서버 측 상태가 필요
- Admin 도구를 CLI에서 웹 UI로 전환하려면 API Routes 필요

**왜 지금 안 하는가:**

- 비용·운영 부담 증가 (Cloud Run min-instances 0이라도 GCS·Artifact Registry·로깅)
- 정적 빌드로도 현재 사용자 가치 거의 100% 전달 가능
- AdSense 운영 안정 + 트래픽 증가 신호가 보일 때 전환

### 3.2 전환 트리거 (기획 측면)

다음 중 2개 이상 충족 시 Phase 6 착수:

- 베이비페어 크롤러가 주 1회+ 자동 실행 필요한 데이터 빈도
- 회원가입 의사결정 (PRD Future Features E1)
- DAU 의미 있는 수준 도달 (구체 수치는 Phase 4.5 코호트 데이터 기반 결정)
- 운영자 1인 관리 한계 도달 (수동 데이터 입력 시간 vs 트래픽 가치)

### 3.3 기획 결정 사항

- **데이터 소스 전환 정책**: GCS 마이그레이션 시 기존 사용자 localStorage는 그대로 유지 (서버 동기화는 회원가입 결정 별개)
- **베이비페어 데이터 freshness SLA**: 6시간 vs 24시간 캐시 — 운영 비용 vs 신선도 트레이드오프
- **API Routes 설계**: 공개 GET vs 인증 필요 (Admin) 분리 명확화

## 4. Phase 7 — 운영 배포

> 출처: [`docs/plan/plan.md`](../plan/plan.md) §Phase 7

### 4.1 기획 관점에서의 의미

- Cloud Run + CI/CD + Cloud Scheduler(베이비페어 크롤 일 1회)
- gh-pages 무료 배포 → 비용 발생 단계로 전환

### 4.2 비용 관리 룰 (PRD §운영 체계 인용)

- Cloud Run `min-instances 0` — 트래픽 없을 때 비용 없음
- GCS — 소량 JSON, 비용 무시 수준
- 운영자가 매월 비용 점검. 비정상 트래픽 알림 설정

### 4.3 기획 결정 사항

- **도메인 이전 전략**: gh-pages 도메인 → Cloud Run 도메인 전환 시 SEO 영향 (Phase 4 시점 도메인 일관성 확보됐는지 확인)
- **AdSense 광고 ID**: 도메인 변경 시 AdSense 콘솔 사이트 추가 등록
- **GA4 측정 ID**: 동일 ID 유지 (코호트 데이터 연속성)
